# 并行编排：按冲突域拆分（PARALLEL_ORCHESTRATION）

> 并行不是「多开几个 Agent」，而是把关键路径拆成**可以重叠的等待**。
> 并行收益 = 可同时完成的独立产出 − 沟通、冲突与失效证据的返工成本。
> 并行的是**等待**，合并的是**当前真相**；它来自重叠等待，不来自同时改同一处代码。

---

## 1. 三轮流水线模型

| 轮次 | 可同时进行 | 汇合条件（Barrier） | 节省在哪 |
|---|---|---|---|
| **第一轮：理解** | A 盘点旧工作流；B 画数据/调用链拓扑；C 设计 Automation 与可见 QA 矩阵 | 三条 lane 都返回「结论 + 证据入口 + 未知项」，Coordinator 冻结统一合同 | 三个最耗阅读时间的调查接近最慢一条 lane 的耗时，而非三者相加 |
| **第二轮：交付** | 业务实现、测试代码、QA manifest 各自写独立文件域 | 公共接口已稳定、文件 owner 不重叠、每条 lane 有自己的 Gate | 实现过程中测试与 QA 不再空等 |
| **第三轮：集成** | **停止并行写**，由唯一集成者处理 seam、构建最终二进制 | Diff、测试与任务卡全部回收；接口变化明确作废受影响结果 | 避免合并阶段继续制造分叉 |
| **第四轮：证明** | 只读、独立结果根且项目明确支持隔离的 Automation 可并行 | 本技能 headless runner、真实 Editor、共享 fixture 与桌面输入按项目租约**串行** | 证据全部来自同一最终源码 |

**主动保留串行 Barrier**：公共接口、同一资产、UBT、Editor、fixture、桌面输入和最终完成裁决保持串行。Barrier 不是损失，而是让并行结果重新属于同一个系统。

---

## 2. 角色与文件域（lane 表）

| Lane | 允许写入 | 只读依赖 | 独占资源 / 暂停点 | 自己的 Done |
|---|---|---|---|---|
| **Coordinator** | Plan、任务卡、合同 | 全部 lane 证据 | 公共接口变更会暂停所有写入 lane | 审查证据、冻结合同、唯一集成裁决 |
| **Implementation** | 授权模块 / exact files | 冻结后的公共 API | 不得反向修改框架；seam 不足 → 报告 Blocked | 最小实现 + 负向用例 + focused test 通过 |
| **Research/Review** | 不写产品文件 | 全部调用链、Diff、测试矩阵 | 可全程并行；发现 P0 只回报 Coordinator | 事实/推断分离，给出路径、反例与风险 |
| **QA** | 独立 case manifest、结果目录 | 产品代码与可见 UI 合同 | 执行期独占 Editor、窗口/输入租约、UserDir、结果根目录 | 报告 + 截图 + timing，按最终源码重跑关键 Gate |

**红线**：多个 Agent 可以读取同一个事实，但**不能同时发明多个「当前真相」**。一个文件只有一个写入 owner。

## 3. 资源隔离清单（比代码拆分更容易被忽略）

不同文件仍可能争用同一资源，必须写进任务卡：

```
□ UBT 全局互斥锁（-WaitMutex）：同一时刻只允许一个编译
□ Editor 进程：内置 headless runner 要求机器级独占；发现任何现有或不可枚举的 UnrealEditor 时 fail-closed
□ 端口：引擎内通道/服务端口按 lane 分配
□ Saved 目录 / AssetRegistry / 自动化 worker：只有项目提供并验证独立 UserDir/结果根时才允许并行
□ 桌面输入（截图/按键）：物理上互斥，必须串行租约
□ 测试 fixture：写入 fixture 必须 opt-in，禁止并行污染生产内容
```

## 4. 可直接使用的编排 Prompt 模板

```markdown
请把「<任务第一阶段>」拆成 3 个并行只读子任务，并在全部返回后统一综合；
不要让子任务修改文件。

Lane A · 业务盘点：[盘点真实用户工作流、必须保留的能力]；输出保留/替换/删除清单和证据入口。
Lane B · 数据/调用链拓扑：[列数据源、owner、下游消费者与加载风险]；输出 owner 图、事实/推断和未知项。
Lane C · 验收设计：[从用户结果反推 focused Automation、可见 QA、性能]；输出用例矩阵、fixture 与失败分类。

共同约束：
- 每条 lane 只返回结论、关键证据和未确认项，不粘贴全部搜索日志；
- 不修改公共接口，不启动共享 Editor，不把推断写成事实；
- 若发现会改变另外两条 lane 的前提，立即回报 Coordinator。

汇合后请输出统一合同：
1. 唯一用户结果与 Non-goal；
2. 数据流/调用链图（Source → ... → Consumer）；
3. 公共接口、文件 owner、共享资源与 Barrier；
4. 最小纵向切片和它自己的验收；
5. 第二轮可并行的独立写入任务卡；
6. 最终必须串行执行的 Build / Editor / Runtime Gate。
```

## 5. 并行失败的经典模式

| 模式 | 后果 | 防线 |
|---|---|---|
| 全串行 | 每阶段等上一阶段「彻底结束」，调查与用例设计本可并行 | 第一轮并行消除不同种类的不确定性 |
| 多 Agent 同时写共享文件 | 合并事故、互相覆盖 | 文件 owner 冻结 + Barrier |
| 多个「当前真相」 | 决策冲突、证据失效 | Coordinator 是唯一合同/真相源 |
| 并行跑共享 Editor/UBT | 双实例、锁冲突、证据不可追溯 | 资源隔离清单 + 租约串行 |
| 接口未冻结就分头实现 | 大规模返工 | 第一次 Barrier 冻结合同后才授权写入 |
