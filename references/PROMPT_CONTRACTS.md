# 任务合同与 Prompt 模板（PROMPT_CONTRACTS）

> Prompt 不是一句需求，也不是代码路径清单，而是一份**微型工程规格**。
> 好 Prompt 不一定更长；路径和复现是输入线索，真正决定收敛的是**行为目标、正确性基线、边界、不变量与验收证据**。
> 路径负责定位工作集；现象、约束与验证负责缩小决策空间。

---

## 1. 合同七要素

| 要素 | 内容 | 反例（缺了会怎样） |
|---|---|---|
| **OUTCOME** | 用户最终能看到/测到什么变化 | AI 只改了内部状态，用户可见结果未变 |
| **ORACLE** | 正确行为以什么为准（代码/旧实现/截图/规范/数值） | 各自发明「正确行为」，无法裁决 |
| **SCOPE** | 允许修改的模块、文件与资产 | 范围膨胀，顺手重构 |
| **NO-GO** | 明确非目标与禁止扩大的范围 | 做了一堆没要求的事 |
| **CONSTRAINT** | 兼容、性能、架构、数据安全 | 破坏下游消费者或公共格式 |
| **ACCEPTANCE** | Automation、可见 QA、指标与报告 | 「完成」无法审计 |
| **AUTHORITY** | 可自主推进与必须暂停的边界 | 每步都问，或无限扩面 |

**专业工程师最容易踩的坑**：不是不具体，而是把隐性知识留在自己脑中。熟悉项目的人能准确指出路径，却默认 AI 也知道它为什么存在、谁依赖它、什么不能变。

## 2. 长任务合同（模板）

```markdown
你是我的结对开发者。请先只读检查指定范围，再完成以下目标。

目标（OUTCOME）：
- [用户可观察的最终结果]

当前事实 / 正确性基线（ORACLE）：
- [现状、权威入口、旧行为或参考实现]
- 不确定内容必须从仓库或运行证据确认，不要猜测。

本轮范围（SCOPE）：
- 允许修改：
- 禁止修改：
- 明确非目标（NO-GO）：

必须保持的约束（CONSTRAINT）：
- 架构边界：
- 兼容与回退：
- 性能与数据安全：
- 不允许的隐式行为：

验收（ACCEPTANCE）：
- 功能：
- AutomationTest：
- 可见 QA：
- 性能：
- 最终证据：

工作方式（AUTHORITY）：
1. 先复述理解、风险与最小实现路线；
2. 用 Plan 维护当前阶段与 Gate；
3. 每轮只完成一个可独立验证的切片；
4. 修改后运行 exact-file gate 与 focused tests；
5. 扩大范围、破坏性操作或改变架构前暂停；
6. 最后报告修改、证据、遗留风险与下一 Gate。
```

## 3. 聚焦修复（模板）

```markdown
问题：
- [可稳定复现的用户现象]

先诊断，不要立即重构：
- 追真实调用链并区分根因、触发条件和表象；
- 明确哪些判断是事实，哪些仍是推断；
- 找到最小修复 seam。

边界：
- 只允许修改：[exact files / module]
- 不做：[邻近重构、行为升级、兼容扩面]

验收：
- 失败用例先能稳定复现；
- focused Automation 覆盖根因与反例；
- 若是 UI/生命周期问题，必须补真实可见操作；
- 任何最终测试后的源码修改都会使旧证据失效。
```

## 4. 只读审计（模板）

```markdown
请对 [范围] 做只读审计，不修改文件、不运行会写资产的命令。

重点回答：
1. 当前实现的真实数据流、所有权与生命周期；
2. 与目标合同的差距，按 P0 / P1 / P2 排序；
3. 每个结论的代码或运行证据；
4. 哪些证据缺失，不能宣称什么；
5. 最小修复顺序与每阶段 Exit Gate。

输出要求：事实与推断分开；不要用低层测试替代高层用户证据。
```

## 5. 失败后重定向（模板，★ 打破 Zero-Delta Retry）

```markdown
上一轮没有通过验收。请暂停继续打补丁，回到诊断阶段。

Expected：
- [应该发生什么]

Actual / 稳定复现：
- [现在发生了什么]
- [步骤、环境和触发条件]

上一轮修改：
- [改了什么]
- [它证明了什么]
- [它没有证明什么]

本轮新增证据：
- 日志 / 截图 / UI 状态：
- 数据读回：
- 通过与失败的对照用例：

需要作废或重新验证的假设：
- [...]
```

> **为什么需要它**：没有新增 Expected/Actual、日志或被否定假设的「继续」，会让 AI 沿旧方向继续打补丁。每轮结束都应新增事实、减少候选根因、明确下一项实验。

## 6. 中途引导 STEER（对当前任务的中途插入）

```markdown
这是对当前任务的中途引导，不是新目标。

保持不变（KEEP）：
- 用户最终要得到的结果：[...]
- 已确认事实与验收标准：[...]
- 允许修改与禁止扩大的范围：[...]

新增证据（DELTA）：
- 实际现象 / 日志 / 截图：[...]

因此作废（INVALIDATE）：
- 旧假设 / 实现方向 / 旧证据：[...]

请在下一个安全中断点：
1. 停止基于旧假设继续扩写；
2. 说明已完成动作是否仍然有效；
3. 更新 Plan 与候选根因；
4. 先给区分度最高的下一项检查，再决定是否继续修改。

不要扩大原写入范围。
```

**中途消息路由判断**（新信息该去哪）：
- **STEER（现在进当前任务）**：新证据直接改变当前候选根因。
- **QUEUE（留到当前任务后段）**：属同一交付但依赖正确性先稳定（如先证明正确，再测延迟/规模）。
- **NEW TASK（独立上下文）**：有独立的用户结果、数据安全风险和分支矩阵——**代码相邻 ≠ 同一任务**。

## 7. 排队 QUEUE（模板）

```markdown
这是当前任务的后续队列，请不要改变眼前修复与验收。

当前阶段完成并汇报后，再处理：
- 后续结果：[...]
- 它依赖当前阶段的什么结果：[...]
- 允许修改的范围：[...]
- 验收标准：[...]

开始后续阶段前，先复述当前修复的最终结果、剩余风险，
并确认这条队列消息仍然适用；若前置结果失败，将它标记 Deferred。
```

## 9. 上下文恢复（模板，检测到漂移时用）

```markdown
暂停继续写代码。当前回答把旧的 PASS 当成了最新证据，可能已经发生上下文漂移。

请先执行上下文恢复，不要凭聊天摘要继续：
1. 重读当前目标、规则、最新 Plan、当前 Diff 和最后一份证据报告；
2. 输出「仍有效事实 / 已失效证据 / 未验证项 / 禁止事项」，并为每项给出权威入口；
3. 明确指出当前回答与源码或证据冲突的地方，撤回由旧上下文产生的结论；
4. 生成新的 Current Truth Packet（见 WORKFLOW_STATE_MACHINE.md §3.3）；
5. 选择一个区分度最高的最小验证动作。恢复完成前不要扩大范围或继续实现。

当前已知差分：[最后一次修改晚于哪个旧证据；因此该旧证据必须标记为 INVALIDATED]
```

## 10. UE 场景 Prompt 要点速查

写 UE 相关合同时额外固化（来源：实测踩坑，见 `UE_BUILD_PITFALLS.md` / `UE_RUNTIME_GOTCHAS.md`）：

- 「先读引擎源码确认 API 真名再写代码，引用 文件:行号」——引擎 API 名常与直觉不符。
- 「Editor + Game 双 target 都要编译通过」——editor-only 字段差异只有 Game target 能暴露。
- 「涉及序列化/静态注册处，先查 UE_RUNTIME_GOTCHAS.md 对应章节再动手」。
- 「跑 Spec 用 headless 脚本，仅退出码 0 为通过；1–6 分别保留测试、零测试、日志、参数、超时和 runner 故障语义」。
- 「验证必须包含引擎内行为证据（日志/截图/测试输出），编译通过不算验证」。
- 「热 Editor 预览 ≠ 保存 ≠ 冷加载 ≠ 运行时；每层分别证明」。
