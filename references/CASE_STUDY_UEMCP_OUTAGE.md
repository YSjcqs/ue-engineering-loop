# 实测案例锚点：引擎在跑但 UEMCP 连不上（CASE_STUDY_UEMCP_OUTAGE）

> 本篇是 `MCP_CHANNELS.md` §5 排查树与 `EXPERIENCE_INDEX.md` 第 1-2 条的**过程性案例**，提供「这是真实发生过的事」的可信度锚点。
> 沉淀自 2026-08-30 在 `F:/Unreal/Blank` 项目的一次真实闭环验证。结论已回写 SKILL.md 硬规则 1 时序纪律与硬规则 7 降级路径。

---

## 1. 现象

`UnrealEditor.exe` 进程在运行（PID 22448），但探测 `http://127.0.0.1:8000/mcp` 返回 `000`（不可达）。

```
[probe] http://127.0.0.1:8000/mcp  →  HTTP 000  unreachable
[proc ] UnrealEditor.exe  PID 22448  (running)
[net  ] netstat -ano | findstr 8000  →  (no output)
```

---

## 2. 排查过程（按排查树逐步执行）

```
□ 1. 引擎进程在跑？            → 是（UnrealEditor.exe PID 22448 存在）
□ 2. 8000 端口在监听？          → 否（netstat 无 8000 条目）★ 断点
□ 3. 项目是否启用 MCP 插件？     → 否（Blank.uproject 的 Plugins 只有 ModelingToolsEditorMode，
                                     项目目录没有 Plugins/ 目录）★ 根因
□ 4. AutoStart 是否开启？        → 无法确认（插件都没启用）
```

---

## 3. 根因

项目**未安装/未启用 Unreal MCP 插件** → 引擎内没有起 HTTP 服务器 → 8000 端口无监听 → 任何客户端都连不上。

---

## 4. 结论（已写入技能经验）

**「引擎在跑」与「引擎内通道可用」是两回事**。排查顺序必须是：

```
插件启用 → AutoStart → 端口监听 → 探测可达
```

四者缺一即 `000`。任一项断裂都必然导致探测失败，且**断裂点不同，处理动作完全不同**：

| 断裂点 | 处理 |
|---|---|
| 插件未启用 | 询问用户是否启用（SKILL.md 硬规则 7）；拒绝 → 降级路径 |
| AutoStart 未开 | 控制台执行 `ModelContextProtocol.StartServer` 或开启 AutoStart 后重启 |
| 端口未监听 | 查插件启动报错（Saved/Logs）；确认端口未被占用/被改 |
| 探测不可达 | 查防火墙 / MCP 版本兼容 / 客户端配置 URL |

---

## 5. 衍生的时序纪律（★ SKILL.md 硬规则 1 的来源）

本次案例的「插件未启用」是**静态状态**，在任意时刻探测都能复现。但后续在另一次会话中观察到一种更隐蔽的误判：

**编译刚跑完、引擎还没用新产物启动**时，探测 UEMCP 必然 `000`——此时引擎要么没启动，要么跑的是旧代码。如果 AI 据此误判为「插件未装/将降级」，就会在错误的时机做出错误决策。

由此提炼出**时序纪律**：

> 编译阶段**禁止**探测/断言引擎通道状态——此时端口无监听是**正常且必然**的。链接状态必须在「编译成功 + 引擎用新产物启动」之后重新检查，同一会话内是**动态**的。

这条纪律是本案例的**直接产物**，已固化为 SKILL.md 硬规则 1（时序纪律）。

---

## 6. 处理动作（本次案例）

1. AI 停下，向用户报告：「项目未启用 Unreal MCP 插件，8000 端口无监听」。
2. 询问用户是否启用插件（附 `ENVIRONMENT_QUICKSTART.md` §3 启用流程）。
3. 用户选择**不启用** → 进入降级路径（SKILL.md §2.4 R7）：
   - 跳过引擎内自动化测试，在任务卡标注「引擎内自动化测试被跳过（用户未启用 MCP 插件）」；
   - 改走 Workbench 实机验证 + 日志取证；
   - 验证义务不豁免，只是换验证手段；
   - 交接记录中写明「UEMCP 不可用 + 原因 + 用户决策」，下次会话不重复询问。
