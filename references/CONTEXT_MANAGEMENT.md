# 上下文管理与长任务文档体系（CONTEXT_MANAGEMENT）

> 上下文不是聊天历史，而是当前任务的**可执行工作集**。
> 聊天窗口不是项目数据库——每次跨天、切换会话、上下文压缩或暂停前，把当前真相写进**权威检查点**。
> AI 长任务的最大敌人是「上下文丢失」与「文档与实现脱节」；解法是状态外置 + 单一真相源 + 强制交接。

---

## 1. 上下文的四层模型

| 层 | 载体 | 内容 |
|---|---|---|
| **L0** | 当前会话 | 本轮意图、临时判断、正在执行的动作 |
| **L1** | Handoff / STATUS | 当前问题、文件、证据、下一步、Do Not Repeat |
| **L2** | Roadmap / Plan / 阶段文档 | 阶段、决策、不变量、依赖与证据入口 |
| **L3** | Rule / Skill / Automation | 跨任务复用的边界、流程、决策表与脚本 |

**给 AI 更多文本 ≠ 给它更好的上下文**。把整段聊天原样塞回去，会同时带回过时结论、错误假设与已完成的待办。正确做法是维护**当前真相包**（见 §3）。

---

## 2. 高质量上下文的六个组成部分

| 组成 | 说明 |
|---|---|
| **Objective** | 本轮唯一主要结果 |
| **Oracle** | 正确性以什么为准 |
| **Invariants** | 任何实现都不能破坏什么 |
| **Current State** | 当前代码、CL、已完成/未完成 |
| **Evidence** | 哪些测试来自哪一版源码（★ 证据与源码版本的对应关系） |
| **Next Action** | 恢复后最小、确定、可执行的下一步 |

## 2.1 上下文卫生：预防 / 检查点 / 检测 / 恢复 / 利用

1. **PREVENT 把真相放到聊天外**：规则进 Rule/Skill，目标与 Gate 进 Plan，当前状态与证据进 STATUS/Handoff。
2. **CHECKPOINT 在相变前压缩**：进入大改、长日志、编译或真实 QA 前，先写一次 Current Truth。触发时机：Plan 阶段切换、公共接口变化、刚产生大量日志、准备启动引擎/运行时、预计离开较久、即将单开相关任务。
3. **DETECT 识别漂移**：旧假设复活、重复已完成工作、错用旧绿灯、范围突然扩大——都是报警信号。
4. **RECOVER 暂停写入重新锚定**：以规则、当前 Diff、最新源码和证据为准，标记冲突与失效项（恢复 Prompt 见 `PROMPT_CONTRACTS.md` §9）。
5. **EXPLOIT 让机制替你守上下文**：同一结果留在当前会话；独立结果开新会话；噪声调查只回传摘要。

## 3. 压缩规则（什么能丢、什么绝对不能丢）

| 必须保留 | 可以压缩 | 应该丢弃 | 压缩失败的典型后果 |
|---|---|---|---|
| 「不允许做什么」 | 讨论过程 | — | Agent 把禁止项当成开放项重新实现 |
| 当前权威结论 | 重复进度播报 | 被覆盖的旧状态 | 历史 handoff 抢走当前真相 |
| **证据与源码版本的对应** | 大段原始日志 | 旧 DLL/旧进程的结果 | 用上一版绿灯证明当前代码 |
| 未执行 / Blocked | 无关命令细节 | 无法复现的猜测 | 「未测试」被压成「已完成」 |
| Next minimum action | 已关闭问题细节 | 无新证据的旧待办 | 换会话后重复劳动或错误扩面 |

> 上下文压缩应删除过程噪声，但**必须保留因果、否定条件、证据等级与下一步**。

### 3.1 恢复协议（先修正工作集，再恢复执行）

```
停止 → 暂停写入，不让错误上下文继续制造 Diff
重读 → 目标、规则、当前 Plan、最新 Diff 与最近证据
对账 → 把「已完成」逐项与日志时间、源码版本对应
作废 → 明确标记早于最后一次修改的旧绿灯为 INVALIDATED
重锚 → 生成新的 Current Truth Packet，保留禁止项与 NOT RUN
恢复 → 只执行一个区分度最高的最小验证动作
```

## 4. 长任务文档体系（推荐结构）

```
Docs/<Plan>/
├── AGENT.md                 # ★ AI 必读总纲：铁律、工作流、边界、Gate 自检清单
├── STATUS.md                # ★ 唯一状态真相源（看板 + 进度表 + 交接记录 + 勘误候选）
├── 00_ROADMAP.md            # 阶段清单 + 里程碑 + 依赖 + 风险前置（POC 裁决点）
├── references/
│   ├── ENGINE_REFERENCES.md # 引擎源码引用表（API / 文件:行号 / 版本差异）
│   └── DESIGN_*.md          # 设计文档（分册）
├── phases/
│   ├── phase-01-xxx.md      # 一阶段一份（需求 ID / 验收标准 / 实现提示 / API 契约）
│   └── ...
└── scripts/                 # 可复用脚本（健康检查/清理/轮询/构建）
```

### 4.1 一次只打开一份阶段文档（物理隔离，★ 最重要）

```
□ 阶段实现期间：只读 phases/phase-NN-*.md（当前阶段）
□ 前置/后续阶段文档：禁止提前打开（上下文污染 + 提前做后续工作）
□ 索引类文档（AGENT / STATUS / ROADMAP / references）：可随时打开
□ 阶段完成后 → 打开下一份阶段文档
```

**为什么**：阶段文档常含后续阶段的预留设计，提前读到会导致提前实现、偏离当前验收标准。

### 4.2 AGENT.md 应有内容

```
1. 铁律（读门、证据门、禁用某类工具/路径）
2. 时机语义（哪些检查在什么阶段才有效——如引擎通道探测时序）
3. 会话启动检查清单（按顺序逐项打勾）
4. 工作流（读文档 → 读门 → 检索 → 实现 → 自检 → 验证 → 交接）
5. 能力边界（AI 自己解决 vs 必须请用户）
6. 故障排查树
7. 日志驱动等待策略（不用 sleep 轮询）
```

### 4.3 STATUS.md 五区（单一真相源）

| 区 | 内容 | 更新时机 |
|---|---|---|
| **看板** | 当前阶段 / 完成数 / 里程碑 / 阻塞项 | 每次阶段切换 |
| **进度表** | 每阶段：状态 + 验收证据 + commit | 阶段完成 |
| **勘误候选** | 设计文档与实测不符处 | **发现即记** |
| **待人工处理事项** | 编号清单（备测试资产、主观判断验收） | 发现即记 |
| **交接记录** | 每会话一段：产出 / 验收证据 / 踩坑 / 读门记录 / 检索结论 / 下一步 | 会话结束 |

**交接记录模板**：

```markdown
### [日期] · 会话 N · P<编号> <状态> · <一句话标题>
- 产出文件（N 新 + M 改）
- 验收证据（逐条对应验收标准，附证据）
- 读门记录（API: 文件:行号 + 结论）
- 网络检索记录（N 条：问题 → 结论 → 来源）
- 踩坑实录（现象 → 根因 → 修复）
- 勘误候选
- 下一步
```

## 5. 勘误候选机制（★ 保持文档与实现同步）

**规则**：发现设计文档/阶段文档/契约表与实测不符 → 写进 STATUS.md「勘误候选」区，**不修改原文档**。

- 记录格式：`章节 → 文档说法 → 实测结论 → 本阶段如何处理`。
- 原因：原文档可能是用户/设计者的权威输入，AI 无权擅自改；勘误区做「可追溯的偏差记录」。

**典型勘误类型**：

```
□ API 名不存在（文档写 Contains，实际 HasTag）
□ 配置位置错误（文档说 DefaultEngine.ini，实际 DefaultEditorPerProjectUserSettings.ini）
□ 语义描述错误（文档说 Unhandled 会 fallback，实际是静默无操作）
□ 宏签名变化（文档 3 参，实际需要 5 参）
□ 设计文档章节缺失/不可读 → 实现为假设，标注 [INFERRED]
```

### 5.1 假设声明 [INFERRED]

设计文档缺失或不可读而需自行决策时，**必须在代码注释与交接记录里标注**：

```cpp
// [INFERRED] 设计文档 §x.y 不可读/未定义，此处实现为「最小时间窗」，P11 校正
```

禁止把假设包装成「文档要求」。

## 6. Git 工作流

```
□ 仓库范围：只管需要版本化的目录（如 Plugins/<Plugin>），不含 Docs/Config/Saved
□ 每阶段独立 commit：`P<NN>: <一句话描述>`
□ .gitignore 排除：Binaries/、Intermediate/、IDE 缓存
□ 阶段通过验收后再 commit（不提交未验证的中间态）
□ Bug 修复独立 commit：`P<NN>-fix: <描述>`
```

**零改框架证明**：`git diff --stat` 只显示新增文件 + 少量依赖声明、框架文件零改动 = 架构解耦成立的直接证据（架构类验收可用此法）。

## 7. 会话启动检查清单（模板）

```
□ 1. 读 AGENT.md（完整）
□ 2. 读 STATUS.md（完整）
□ 3. 读 ENGINE_REFERENCES §0（版本勘误）
□ 4. 读 00_ROADMAP.md（定位当前阶段）
□ 5. 能力探测（env_health_check.ps1：通道 + 进程 + 端口）
□ 6. 打开当前阶段文档（只此一份）
□ 7. 需求门：向用户复述目标/验收标准
```

## 8. 最小骨架模式（处理循环依赖）

后续阶段才定义的完整类型，当前阶段需要 typed 引用时，建**最小骨架**并注释声明：

```cpp
/**
 * P<NN> MINIMAL SKELETON: 仅为让 A 持有 typed 引用而存在。
 * P<MM> 扩展为完整实现。Do not add engine-facing members here before P<MM> — extend, don't fork.
 */
```

原则：**extend, don't fork**——禁止绕开骨架另起炉灶造成分叉。
